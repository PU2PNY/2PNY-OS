# PU2PNY-OS 0.2.8 — plano mestre consolidado

## Regra de base
A 0.2.8 nasce da 0.2.7 sem alterar a release publicada. A base anterior foi preservada em `backup/pre-0.2.8-20260918`.
O DMR aprovado na 0.2.6/0.2.7 é uma regressão obrigatória: nenhuma função nova pode modificar silenciosamente RF, baud, offsets, DMRGateway ou HMI/TFT.

## Identidade do produto
PU2PNY-OS é a distribuição e experiência do produto. Painel, wizard, rede, atualização, controle remoto, Direct, banco local, telemetria, diagnóstico, telas e UX são PU2PNY.
Motores consolidados como MMDVMHost, DMRGateway, MMDVM-Display, Linux e bibliotecas de criptografia continuam componentes internos de terceiros com licenças preservadas; não devem definir a marca nem a experiência do usuário.

## Estado confirmado na 0.2.7
- Imagem ARM64 publicada e validada em CI; teste físico de Wi-Fi/mDNS/Nextion ainda necessário.
- DMR com MMDVMHost -> DMRGateway -> rede externa preservado.
- Wi-Fi/AP com recuperação, Ethernet independente, `pu2pny.local`/Avahi e acesso por IP.
- Ao Vivo TX/RX, histórico local, RadioID, filtros, telemetria e modo Expert.
- Nextion direta e Nextion via MMDVM/MMDVM-Display; HMI/TFT não é sobrescrito.
- Auto-maintenance atual só faz índices/firmware/listas e explicitamente não é atualização completa do PU2PNY-OS.
- Rollback atual cobre a aplicação transacional de RF/serviços relacionados, não uma atualização remota completa do sistema operacional.

## Lacunas reais recuperadas das conversas

### PU2PNY Direct / ponto a ponto
Ainda não implementado. Requisito:
1. Dois hotspots PU2PNY devem poder falar diretamente pela Internet, sem o áudio passar por servidor quando o caminho P2P UDP for possível.
2. Descoberta/rendezvous pode usar o PU2PNY Control, mas o plano de dados deve ser direto.
3. NAT traversal deve seguir ICE/STUN. Em CGNAT/hard NAT onde o P2P for impossível, usar relay/TURN próprio como fallback.
4. Criptografia ponta a ponta; chaves privadas permanecem no hotspot.
5. Indicador no painel: `Direto`, `Relay`, latência e qualidade.
6. Primeiro somente mesma modalidade/protocolo compatível. Cross-mode exige ponte/transcoding e fica separado.
7. Pareamento simples por indicativo/ID + autorização explícita do dono do hotspot.

### Acesso e controle remoto
Ainda não existe como produto PU2PNY completo. Requisito:
1. Hotspot sempre inicia conexão de saída; nenhuma porta de entrada deve ser obrigatória para funcionar atrás de CGNAT.
2. Cada equipamento recebe identidade criptográfica própria no primeiro provisionamento.
3. PU2PNY Control mantém apenas inventário, presença, comandos autorizados, versão, saúde e rendezvous.
4. Administração remota deve usar túnel autenticado e limitado; não expor root nem senha padrão.
5. Ações remotas auditadas: verificar saúde, reiniciar serviços permitidos, baixar diagnóstico, atualizar, restaurar versão anterior e reiniciar.
6. Comando remoto destrutivo deve ser transacional e reversível quando tecnicamente possível.

### Atualização remota e rollback de sistema
Ainda não implementado. Meta: atualização A/B com recuperação automática.
1. Layout futuro de imagem com dois slots de sistema (A/B) e dados persistentes separados.
2. Atualização sempre gravada no slot inativo; nunca sobrescrever o sistema em execução.
3. Artefato assinado + SHA-256 + compatibilidade de hardware/versão antes da instalação.
4. Reboot de teste usando o mecanismo `tryboot` do Raspberry Pi quando aplicável.
5. Health gate após boot: rede, 2pnyd, painel, MMDVMHost quando configurado, DMRGateway quando configurado, filesystem e temperatura.
6. Somente após o health gate marcar a nova versão como boa.
7. Se não subir, travar ou falhar no health gate, voltar automaticamente ao slot anterior.
8. Botão no painel e no PU2PNY Control: `Restaurar versão anterior`.
9. Separar atualização do PU2PNY-OS de atualização de listas/firmware/índices.
10. Canal Stable / Beta / Dev, padrão Stable.
11. Atualização automática deve ser opcional e ativável/desativável; download pode ocorrer em segundo plano, ativação só com janela segura e sem TX/RX ativo.
12. Backup de configuração antes de toda mudança: rede, RF, protocolo, servidor, display, usuário e chaves públicas; nunca copiar segredos em log.

### Displays físicos
A detecção atual encontra Nextion, candidatos USB/I2C/SPI e saídas de vídeo, mas o aplicador da 0.2.7 só configura Nextion. Portanto, OLED/LCD/TFT não estão concluídos.

Criar `pu2pny-display-core` com drivers independentes:
- Nextion direta.
- Nextion via MMDVM/MMDVM-Display.
- OLED SSD1306/SH1106 I2C/SPI.
- LCD HD44780 direto/I2C backpack.
- TFT SPI comuns quando driver do kernel existir.
- Display serial genérico onde houver protocolo conhecido.
- Saída framebuffer/HDMI opcional em modo kiosk, sem substituir o painel web.

Modelo de dados único para todas as telas:
- boot: PU2PNY-OS, versão e progresso resumido;
- rede: AP/Wi-Fi/Ethernet, IP e Internet;
- rádio: MMDVM/firmware/porta/baud;
- standby: indicativo, protocolo, servidor/refletor/TG/módulo, IP, temperatura;
- TX: direção, indicativo, destino, TG/refletor, slot, duração, BER/RSSI quando disponíveis;
- RX: origem, nome/ID quando disponível, destino, slot, duração;
- erro: causa curta + ação segura;
- update: baixando, validando, instalando slot B, testando, concluído ou revertido.

A tela nunca deve bloquear inicialização do hotspot. Falha de display é degradável. HMI/TFT do usuário nunca é sobrescrito automaticamente.

### Painel e wizard
Pendências:
- Status do PU2PNY Direct e controle remoto.
- Tela `Sistema > Atualizações` com versão, canal, verificar, baixar, instalar, histórico e rollback.
- Backup/restauração de configuração com arquivo exportável e restauração validada.
- Seção de displays mostrando tipo, barramento, endereço/porta, driver, layout e teste.
- Completar PT/EN/ES em todo o painel.
- Splash de boot Linux separado da splash web, sem aumentar significativamente o boot.
- Evento em tempo real preferencialmente por SSE/event stream, evitando polling agressivo.
- Estado de rede/AP e mDNS com diagnóstico simples e instrução por IP quando nome local falhar.

Requisitos:

- Quando o catálogo do refletor informar módulos válidos, mostrar somente os disponíveis; quando não houver catálogo confiável, permitir seleção manual A–Z no modo Expert.

- Mostrar o módulo ativo no Ao Vivo, Histórico e Display físico.

- Durante testes, permitir trocar de módulo sem refazer todo o wizard; a mudança deve ficar na página `Protocolos > D-Star`.
- Validar a letra antes de aplicar e rejeitar qualquer valor fora de A–Z.
- Não assumir que todos os refletores aceitam todos os módulos; usar catálogo/capacidade quando disponível.

## Arquitetura PU2PNY Control
O serviço central não deve ser o caminho obrigatório do áudio quando houver P2P. Funções:
- registro de dispositivo e chave pública;
- presença/heartbeat;
- catálogo de versões e manifesto assinado;
- fila curta de comandos remotos;
- rendezvous ICE/STUN;
- relay/TURN próprio somente quando conexão direta não for possível;
- telemetria mínima e opt-in;
- auditoria por dispositivo;
- nenhuma senha do usuário em texto puro.

## UI/UX e telemetria ao vivo — referência XLX026, adaptada ao hotspot

### Princípio
Usar o XLX-Modern-Dashboard apenas como referência de comportamento para baixa latência, QRZ e MTR. O PU2PNY deve ter implementação própria e mais leve para Raspberry Pi. Não copiar a arquitetura PHP do servidor para o hotspot.

### Navegação fixa e agrupada
O menu deve permanecer fixo no desktop e virar barra/menu compacto responsivo no celular, sem sumir durante rolagem. Estrutura alvo:
- Ao Vivo
- Internet
- Hotspot
- Protocolos
  - DMR
  - D-Star
  - YSF/C4FM
  - P25
  - NXDN
  - demais quando instalados
- APRS
- Histórico
- Display
- Sistema
  - Atualizações
  - Backup/Restauração
  - Diagnóstico
  - Expert

Itens sem função instalada podem ficar ocultos ou marcados como não configurados; não mostrar páginas vazias.

### Ao Vivo — somente um box
A página principal após a configuração deve exibir apenas UM box de transmissão, inspirado visualmente no Ao Vivo do XLX026.
- Standby: um único box mostrando hotspot pronto, protocolo selecionado, servidor/refletor/TG e estado da rede.
- Durante RF -> rede: o mesmo box muda para TX.
- Durante rede -> RF: o mesmo box muda para RX.
- Nunca criar dois boxes TX/RX simultâneos como na 0.2.7.
- Em caso de eventos concorrentes, mostrar o evento efetivamente ativo no modem e preservar o outro no histórico.
- Não recriar o DOM a cada amostra: atualizar somente campos que mudaram.
- Foto/identidade não pode atrasar o aparecimento do box; primeiro renderizar indicativo/dados locais e enriquecer depois.

Campos do box:
- direção TX/RX;
- protocolo em uso;
- indicativo/ID/nome;
- foto quando disponível;
- TG/refletor/módulo/DG-ID;
- slot/color code conforme protocolo;
- duração em tempo real;
- BER em tempo real quando fornecido pelo modem/protocolo;
- RSSI/força RF em tempo real quando fornecido pelo modem;
- medidor de sinal RF;
- MTR/rede: latência, perda e jitter até o servidor ativo;
- estado Direct/Relay quando PU2PNY Direct estiver em uso.

### Atualização ao vivo e desempenho
Meta perceptiva: início/fim da transmissão deve aparecer praticamente instantâneo.
Arquitetura:
1. Um worker local lê eventos MMDVMHost/gateways uma vez e mantém snapshot em memória.
2. Browser recebe alterações por SSE/event stream. WebSocket só se houver necessidade bidirecional futura.
3. Fallback para polling adaptativo apenas em navegadores sem SSE.
4. Nenhuma rota HTTP deve reler logs grandes, chamar comandos pesados ou consultar Internet a cada refresh.
5. Identidade, QRZ, RadioID e catálogos usam cache e enriquecimento assíncrono.
6. O DOM do Ao Vivo só é reconstruído quando muda a identidade da transmissão; duração, BER, RSSI, MTR e VU atualizam seus próprios campos.
7. Pausar atualizações visuais quando a aba estiver oculta, mantendo o worker do sistema independente.
8. Compartilhar snapshot entre abas quando possível para não multiplicar trabalho.
9. Não usar animações contínuas caras em Raspberry Pi/telefone antigo.

Metas iniciais:
- evento local -> snapshot: <=100 ms quando a fonte permitir;
- snapshot -> navegador em LAN: alvo <=250 ms;
- atualização BER/RSSI: 4 a 10 amostras/s somente durante transmissão, conforme a fonte;
- duração visual: relógio no browser, sem tráfego de rede por segundo;
- RSS do serviço PU2PNY ao vivo: medir e manter mínimo; nenhum crescimento contínuo;
- não gravar telemetria de alta frequência no SD.

### BER em tempo real
Não esperar somente a linha de fim da transmissão.
- Consumir evento/JSON/telemetria do MMDVMHost quando disponível.
- Manter último BER válido por stream/slot.
- Atualizar o box enquanto a transmissão estiver ativa.
- No encerramento, persistir apenas resumo necessário no histórico.
- Protocolos que não oferecem BER devem mostrar "—", nunca um valor estimado.

### Medidor RF (não chamar RSSI de VU de áudio)
Criar um medidor visual de força do sinal recebido pelo hotspot, estilo VU/S-meter, mas tecnicamente rotulado "Sinal RF".
- Fonte: RSSI real reportado pelo MMDVMHost/modem.
- Exibir dBm quando calibrado e disponível.
- Barra suave com mínimo/médio/pico da transmissão.
- Se o firmware/modem não fornecer RSSI confiável, mostrar "RSSI indisponível"; nunca inventar.
- VU de áudio fica separado e só será habilitado onde existir PCM/nível de áudio real.

### MTR/rede em tempo real
Referência visual: XLX026 mostra LAT/PER/JIT e tendência. No hotspot a implementação deve ser mais leve:
- NÃO executar um processo mtr completo por navegador ou a cada atualização.
- Um coletor local único mede o servidor ativo.
- RTT/perda/jitter: atualização de aproximadamente 1 s durante uso; reduzir cadência em standby.
- Rota/hops: atualizar em intervalo maior ou sob demanda.
- Manter pequeno histórico circular somente em RAM.
- SSE envia apenas a mudança dos números.
- Box mostra LAT, PER, JIT, tendência e estado bom/atenção/ruim.
- Página Internet mostra detalhes de interface e diagnóstico de rota.

### Foto pública QRZ
Replicar o comportamento funcional do XLX026 com cache local:
1. Consultar primeiro cache local pelo indicativo.
2. Quando autorizado/possível, preferir QRZ XML API e o campo oficial `image`.
3. Como fallback opcional para perfil público, consultar `https://www.qrz.com/db/CALL`, ler `og:image` e aceitar somente HTTPS de host QRZ/CDN permitido.
4. Nunca fazer fetch de imagem no ciclo do Ao Vivo.
5. Limitar tamanho, validar MIME real, timeout curto, SSL obrigatório e cache positivo/negativo.
6. Se QRZ estiver lento ou indisponível, usar avatar PU2PNY sem atrasar transmissão.
7. Não expor credenciais QRZ para o navegador.

### Internet — página própria
Exibir:
- Ethernet/Wi-Fi/AP;
- interface ativa;
- SSID, qualidade do Wi-Fi e sinal;
- IP, máscara, gateway, DNS;
- Internet online/offline;
- mDNS/pu2pny.local;

### Hotspot — página própria
Exibir:

- CPU, temperatura, RAM, uptime, armazenamento e saúde do SD;
- MMDVM detectada, firmware, porta, baud, simplex/duplex;

- display detectado e driver;

- serviços PU2PNY e suas versões;

### APRS

- última posição transmitida;
- status da conexão;
- histórico curto;
- mapa opcional carregado somente ao abrir a página para não pesar o Ao Vivo.

Reduzir a primeira configuração para QUATRO janelas:

## Revisão do mock visual de 18/09/2026 — correções obrigatórias antes de implementar

O mock do Ao Vivo aprovado como direção visual precisa das seguintes correções para não mostrar estados falsos ou dados estáticos:

1. `Conexão: Direto` só pode aparecer quando o PU2PNY Direct estiver realmente implementado e a sessão atual estiver comprovadamente P2P. Até lá mostrar o transporte real: servidor/rede configurada, ou `Não disponível`.
2. `BER (última)` deve virar `BER` durante transmissão e ser atualizado em tempo real quando a fonte fornecer. No histórico, manter BER final/resumo.
3. RSSI/Sinal RF só podem aparecer com dados reais do modem/MMDVMHost. O mock usa valores sintéticos apenas para validação visual; produção deve exibir `—`/indisponível quando não houver fonte confiável.
4. LAT/PER/JIT do mock são apenas dados sintéticos. Em produção devem vir do coletor local único e nunca de valores hardcoded.
5. Data/hora devem vir do relógio real do sistema/navegador; remover qualquer data fixa de mock.
6. A versão exibida no rodapé deve vir da versão real do PU2PNY-OS. Não mostrar `v1.0.0` enquanto o sistema estiver em 0.2.8-alpha.
7. `Atualizar servidores` não deve poluir a página Ao Vivo. Mover para `Protocolos` ou para a configuração da rede correspondente. A página Ao Vivo deve priorizar transmissão e atividade.
8. Filtros DMR/D-Star/YSF/P25/NXDN na página Ao Vivo devem atuar somente sobre histórico/atividade; eles não devem mudar silenciosamente o protocolo ativo do hotspot.
9. Padronizar o menu como `APRS`, sem hífen em DPRS.
10. O menu superior deve ser realmente fixo/sticky em desktop e permanecer acessível no mobile, não apenas parecer fixo no screenshot.
11. A tabela `Atividade recente` deve ser limitada no Ao Vivo (por exemplo 6–10 linhas) e o histórico completo fica na página Histórico; isso reduz DOM e mantém a tela leve.
12. O box deve aparecer imediatamente com dados locais mínimos. Foto QRZ, nome, cidade e demais enriquecimentos entram depois sem alterar layout nem reiniciar o contador.
13. A mesma estrutura do box deve servir TX e RX; apenas estado, borda, rótulos e campos aplicáveis mudam.
14. Nenhum campo de mock/sintético pode sobreviver no build de release sem marcação explícita de teste.


## Decisão de escopo — APRS somente
- O PU2PNY-OS deve oferecer **APRS**.
- **DPRS não faz parte do escopo atual e não deve aparecer no menu, wizard, painel, documentação ou testes da 0.2.8.**
- Qualquer referência antiga a APRS/DPRS deve ser tratada como APRS.


## Catálogos, servidores e dados — completos sem poluir a interface

### Princípio
O PU2PNY-OS deve manter os catálogos completos localmente, mas nunca apresentar uma lista única extensa ao usuário. A navegação deve ser progressiva e contextual:

`Protocolo → Rede/Família → Servidor/Refletor → Destino/Módulo`

Exemplos:
- DMR → BrandMeister / TGIF / FreeDMR / DMR+ / XLX / outras → servidor → TG/módulo quando aplicável.
- D-Star → XLX / REF-DPlus / DCS / XRF-DExtra → refletor → módulo A–Z conforme capacidade.
- YSF/C4FM → YSF / FCS quando suportado → servidor/sala.
- P25 → rede/servidor → TG.
- NXDN → rede/servidor → TG.
- APRS → servidor/rede APRS conforme a implementação da função.

### Pronto desde o primeiro acesso
A imagem deve incluir um snapshot inicial validado dos catálogos públicos necessários. Portanto:
1. O wizard nunca deve depender de baixar listas para poder abrir.
2. Ao entrar em Configurações, o sistema mostra imediatamente o último catálogo local válido.
3. Se houver Internet, inicia atualização silenciosa em segundo plano.
4. Quando a atualização terminar, o backend troca o catálogo de forma atômica e envia evento para a interface recarregar a lista sem perder a seleção atual.
5. Se a Internet estiver lenta ou offline, o usuário continua configurando normalmente com o cache local.
6. Uma lista nova só substitui a anterior depois de validação de formato, quantidade mínima e sanidade.

### Atualização automática
Todos os dados externos devem ter uma política própria de atualização; não usar um único polling rápido para tudo.

- Listas de servidores/refletores/hosts: atualizar automaticamente após obter Internet no boot e depois em intervalo moderado, com jitter para evitar picos.
- TGs/catálogos de destinos: atualizar junto da família correspondente.
- RadioID/diretórios: cache local e atualização incremental/periódica.
- QRZ: somente sob demanda por indicativo, com cache positivo/negativo; nunca varrer QRZ.
- Estado de rede, TX/RX, BER, RSSI e MTR: tempo real em memória/SSE, sem gravação de alta frequência no SD.
- Versão/manifesto PU2PNY: checagem periódica separada.
- Dados que não mudaram não devem ser regravados.

### Botão manual de atualização
Cada área de Protocolos deve ter um botão discreto `Atualizar listas`.
Também pode existir `Sistema > Dados > Atualizar tudo` para manutenção.

O botão:
- atualiza em segundo plano;
- mostra progresso por categoria;
- não apaga o cache atual antes de validar o novo;
- não interrompe TX/RX;
- não reinicia MMDVMHost/gateways só porque um catálogo mudou;
- preserva a seleção do usuário;
- informa `Atualizado agora`, `Usando cache` ou `Falha ao atualizar; lista anterior mantida`.

### Interface sem lista gigante
No modo Básico:
1. Mostrar cartões/botões dos protocolos.
2. Depois mostrar somente as famílias daquele protocolo.
3. Depois mostrar `Recomendados/Próximos`, `Recentes` e um campo de pesquisa.
4. A lista completa fica pesquisável sem renderizar centenas/milhares de opções de uma vez.
5. Usar busca incremental/virtualização quando o catálogo for grande.
6. Priorizar por contexto/região quando houver metadados confiáveis, sem esconder servidores de outras regiões.
7. Favoritos e recentes devem ficar no topo.
8. Um botão `Ver todos` revela o catálogo completo da família selecionada.

No modo Expert:
- permitir endereço/porta manual;
- mostrar origem do catálogo, data da última atualização e campos técnicos;
- nunca exigir o modo Expert para operações normais.

### Separação de conceitos
Não misturar no mesmo controle:
- `Modo de equipamento`: Hotspot simplex / Repetidora duplex.
- `Protocolo RF/rede`: DMR / D-Star / YSF-C4FM / P25 / NXDN / APRS.
- `Rede/Família`: BrandMeister, TGIF, XLX, REF, DCS, XRF etc.
- `Servidor/Refletor`: host concreto selecionado.
- `Destino`: TG, módulo, sala, DG-ID etc.
- `Operação avançada`: normal / PU2PNY Direct / cross-mode quando realmente implementados.

### D-Star em particular
Depois de selecionar a família e o refletor:
- mostrar o seletor de módulo imediatamente;
- usar os módulos anunciados/conhecidos pelo catálogo quando disponíveis;
- se não houver informação confiável, permitir A–Z no Expert;
- manter `Refletor + Módulo` como uma única seleção lógica no estado, por exemplo `XLX026 D`;
- o botão de atualizar listas deve atualizar também metadados de módulos sem desconectar a sessão atual.

### Cache e integridade
- Cache persistente pequeno, com versão/schema e timestamp.
- Atualizações baixadas para arquivo temporário e somente promovidas por rename atômico após validação.
- Preservar o último cache bom em qualquer falha.
- Deduplicar entradas por protocolo/família/endereço/porta/ID apropriado.
- Nunca guardar senhas no catálogo público.
- Registrar hash e origem das listas para diagnóstico.
- Limitar logs e evitar reescrita repetitiva do SD.

### Critérios de aceite
- Abrir o wizard sem Internet e conseguir chegar à seleção de protocolo/servidor usando o snapshot embarcado.
- Ao conectar Internet, listas atualizam sozinhas sem bloquear a tela.
- Atualização concluída aparece na UI sem F5.
- Uma lista pública quebrada não substitui a lista válida.
- Nenhum protocolo suportado fica sem catálogo por falha de agrupamento visual.
- Catálogo com milhares de entradas não cria milhares de elementos DOM de uma vez.
- Quatro navegadores abertos não iniciam quatro downloads/atualizadores de catálogos.
- O usuário comum consegue configurar DMR ou D-Star sem usar modo Expert.


## Display Core — boot físico imediato e telas adaptativas

### Objetivo
Qualquer display suportado deve participar do boot e depois assumir automaticamente o modo Ao Vivo, com quantidade de informação proporcional ao tamanho/capacidade da tela.

### Regra de boot
Ao energizar o hotspot:
1. O serviço de display deve subir o mais cedo possível, antes do MMDVMHost e do painel web.
2. Se já existir perfil de display validado de um boot anterior, usar esse perfil imediatamente, sem repetir detecção completa.
3. Mostrar `PU2PNY` e estado de inicialização assim que o barramento/driver do display estiver disponível.
4. A barra de progresso deve refletir marcos reais de inicialização; nunca usar um timer falso.
5. A Internet NÃO é requisito para chegar a 100%. Se a rede externa estiver offline, o sistema chega a `100% / Pronto` e depois mostra o estado de Internet separadamente.
6. Ao atingir 100%, fazer transição automática para a tela Ao Vivo resumida.
7. Falha ou ausência do display nunca pode atrasar o boot do rádio/hotspot.

### Boot bilíngue PT/EN
Antes de existir preferência de idioma, ou durante o boot físico, usar português e inglês.
Em telas médias/grandes, mostrar simultaneamente:
`PU2PNY iniciando / Starting`

Em telas pequenas, alternar mensagens curtas sem animação pesada:
- `PU2PNY`
- `Iniciando...`
- `Starting...`
- barra/percentual

Depois que o sistema estiver pronto, respeitar o idioma escolhido pelo usuário para as telas normais. O usuário pode manter modo bilíngue se desejar.

### Progresso por marcos reais
A implementação deve calcular o percentual por estado concluído, não por tempo decorrido. Referência inicial:
- 5–10%: filesystem/estado local disponível;
- 15–25%: driver/display pronto;
- 30–40%: subsistema de rede local/AP pronto;
- 45–60%: serviços PU2PNY principais;
- 65–80%: MMDVM/hardware e configuração RF disponíveis;
- 85–95%: protocolo/gateway configurado quando aplicável;
- 100%: hotspot operacional e painel/backend disponíveis.

Se algum serviço opcional não estiver configurado, ele não deve impedir 100%. O status final mostra o que está offline/não configurado.

### Perfil persistente do display
Após detectar/configurar com sucesso, salvar um perfil mínimo e versionado contendo apenas dados necessários ao boot:
- classe/tipo;
- barramento;
- porta/endereço;
- velocidade;
- resolução/linhas/colunas;
- rotação;
- driver;
- integração direta ou via MMDVM;
- layout seguro;
- timestamp/versão do perfil.

Esse perfil deve permitir renderização precoce no próximo boot sem abrir a UART do modem indevidamente.

Se o display desaparecer ou o perfil falhar repetidamente, abandonar rapidamente o perfil, continuar o boot e solicitar nova detecção em background.

### Drivers suportados — base embarcada, ativação seletiva
Não instalar indiscriminadamente todos os drivers existentes. A imagem deve trazer suporte para famílias comuns e leves, ativando somente o necessário.

Base obrigatória:
- Nextion Basic/Enhanced/Intelligent compatível, direta por UART/USB-TTL;
- Nextion via canal serial da MMDVM quando suportado;
- OLED SSD1306 128x64;
- OLED SH1106 quando suportado pelo Display Core;
- HD44780 16x2, 20x4 e variantes comuns;
- HD44780 via PCF8574/I2C;
- LCDproc como ponte para telas suportadas por ele;
- TFT serial suportada pelo MMDVM-Display, como Surenoo, quando detectada/configurada;
- TFT/framebuffer/SPI já suportada pelo kernel/overlay validado;
- HDMI/framebuffer opcional em modo kiosk.

Drivers/pacotes maiores ou específicos ficam em módulos opcionais instaláveis pelo próprio PU2PNY somente quando o hardware exigir. Instalação de driver não pode acontecer no caminho crítico do boot normal.

### Detecção
Combinar:
- resposta de protocolo real quando existir;
- USB VID/PID e metadados;
- I2C address scan seguro;
- SPI/kernel framebuffer/DRM;
- HAT metadata;
- perfil salvo do último boot.

Endereço I2C isolado é apenas candidato, não confirmação absoluta. Não escrever em dispositivos desconhecidos durante detecção.

### Layout adaptativo por classe de tela

#### Nextion/TFT grande
Após boot, mostrar uma tela Ao Vivo compacta com:
- TX/RX/Standby;
- indicativo;
- nome quando disponível;
- protocolo;
- TG/refletor/módulo/destino;
- slot/color code quando aplicável;
- duração;
- BER;
- RSSI/Sinal RF;
- Internet/servidor;
- IP/temperatura em standby.

Não sobrescrever automaticamente HMI/TFT existente. Quando o layout atual não possuir componentes PU2PNY, usar comandos gráficos seguros/genéricos ou solicitar instalação opcional de layout PU2PNY.

#### OLED 128x64
Exibir somente o essencial, em páginas curtas ou alternância controlada:
- linha 1: TX/RX + protocolo;
- linha 2: indicativo;
- linha 3: TG/refletor/módulo;
- linha 4: duração + BER ou RSSI;
- standby: IP + temperatura/estado de rede.

Evitar scroll contínuo e animações que aumentem CPU.

#### LCD 20x4
Exemplo:
`TX DMR   PU2PNY`
`TG6 TS2 CC1`
`BER 0.3  -88dBm`
`00:40 NET OK`

#### LCD 16x2
Mostrar resumo extremo:
`TX DMR PU2PNY`
`TG6 B0.3 -88`

Em standby:
`PU2PNY PRONTO`
`192.168.x.x`

#### Telas muito pequenas / LED simples
Não tentar mostrar todos os campos.
Prioridade:
1. estado: boot/ready/TX/RX/error;
2. percentual durante boot;
3. indicativo/destino abreviado quando couber;
4. códigos/LEDs para estado quando display alfanumérico não existir.

### Modelo único de dados
Todos os drivers físicos devem consumir o mesmo snapshot do `pu2pny-display-core`.
Nenhum driver deve reler logs do MMDVMHost ou consultar Internet sozinho.

O snapshot inclui:
- boot.progress;
- boot.state;
- system.ready;
- network;
- radio;
- protocol;
- live TX/RX;
- BER/RSSI;
- MTR resumido;
- atualização/rollback;
- erros.

O Display Core converte esse snapshot para o layout adequado de cada tela.

### Atualização Ao Vivo
Depois de 100%:
- mudança TX/RX deve refletir na tela física praticamente junto ao painel web;
- duração é atualizada localmente pelo Display Core;
- BER/RSSI só são mostrados quando reais;
- QRZ/foto não se aplica a telas sem capacidade gráfica adequada;
- telas físicas não devem depender do navegador estar aberto.

### Atualização remota
Durante OTA:
- mostrar `Atualizando / Updating`;
- percentual real de download/gravação/validação;
- `Testando nova versão / Testing update`;
- `Atualizado / Updated` ou `Revertendo / Rolling back`;
- nunca apagar a tela por longos períodos se o driver continuar disponível.

### Segurança e desempenho
- um processo/serviço de display, não um processo por tela/página;
- sem polling agressivo;
- sem escrita de telemetria de alta frequência no SD;
- timeout curto em hardware;
- memória limitada;
- driver com falha entra em backoff;
- nenhuma tela possui autoridade para alterar RF;
- nenhum boot splash pode tomar posse permanente da UART do modem;
- se MMDVMHost assumir a UART, o Display Core deve usar integração suportada/MQTT ou liberar a porta.

### Testes obrigatórios
- boot com Nextion direta;
- boot com Nextion via MMDVM;
- boot com OLED SSD1306;
- boot com LCD 20x4/16x2 ou emulador de driver;
- boot sem display;
- display desconectado durante boot;
- Internet offline;
- Wi-Fi demorando;
- atualização OTA e rollback;
- troca automática Boot → Ao Vivo;
- reinício repetido sem crescimento de memória;
- inglês/português no boot;
- nenhuma regressão no DMR aprovado.
