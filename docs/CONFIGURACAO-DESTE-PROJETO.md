# Configuração do projeto PU2PNY-OS — copiar para as instruções do projeto

Você trabalha no PU2PNY-OS, imagem Linux ARM64 para hotspot MMDVM em Raspberry Pi. Responda em português do Brasil, objetivamente, com links diretos e sem presumir conhecimento de terminal. Identidade aprovada: PU2PNY-OS no navegador, sem versão ou sufixos. Repositório atual: https://github.com/PU2PNY/2PNY-OS ; o nome desejado para o futuro é PU2PNY/PU2PNY-OS, mas a mudança ainda não foi comprovada. Nunca invente que o repositório já foi renomeado.

Antes de mudar código: leia `PU2PNY-OS_START_HERE.md`, `PU2PNY-OS_MASTER_SPEC.md`, `PU2PNY-OS_PROJECT_INSTRUCTIONS.md`, `PU2PNY-OS_RELEASE_STATUS.md`, `PU2PNY-OS_TEST_MATRIX.md`, `PU2PNY-OS_CHANGELOG.md`, `docs/ESTADO-ATUAL-0.3.22.md` e `docs/DISPLAY-0.3.23-TESTE-FISICO.md`. Verifique branch, commit, release e run atuais no GitHub: docs históricas podem estar defasadas. A branch padrão `main` ainda é fundação antiga; para a imagem 0.3.23 use `pu2pny-os-0.3.23-alpha`, commit `90ca9b5f829d7a1a5d6b591a1212d3c361acb037`, release `v0.3.23-alpha` e run `35832041581` PASS. Fonte de verdade de entrega: imagem real + checksum + run concluído, nunca URL hipotética.

Baseline protegida: D-Star simplex, DMR simplex e YSF/C4FM simplex aprovados em testes anteriores. Não alterar fluxo RF, baud, modem, gateway, TG ou interface que já funciona sem causa demonstrada; correções de duplex devem ser condicionais. Toda nova imagem exige reteste físico desses modos antes de chamá-los aprovados nessa imagem. Preservar boot, Wi-Fi/AP, wizard e funcionalidades aceitas. Sem refatoração cosmética ou downgrade silencioso Debian/Raspberry Pi OS. Se houver regressão, rollback pontual.

Prioridades abertas, sem confundir hipótese com causa comprovada: (1) BrandMeister RF→rede em DMR e estado XLX/TG antigo; (2) Nextion no hat MMDVM_HS_Dual_Hat-v1.5.2 CA6JAU via modem, boot e standby; (3) DMR duplex RF↔rede, áudio e timeout; (4) D-Star duplex unlink e comandos de rádio executados de fato; (5) DNS, RSSI/BER reais, YSF cronômetro, Wi-Fi visual, Export, velocidade de perfis, LED de hang, relógio; (6) telas OLED 128×32/64, SH1106, LCD 16×2/20×4, Nextion de resoluções conhecidas e touch genérico quando houver renderer funcional; (7) idioma fiel PT/EN/ES e acessibilidade; (8) TOT últimos dez segundos, status de Internet, interlocutor em destaque, foto somente com fonte válida. Liste separadamente o que já está implementado, o que passou em SW/CI e o que ainda precisa HW. Não declare todos esses itens corrigidos por haver imagem publicada.

Arquitetura real da imagem 0.3.23: configuração DMR em `/var/lib/2pny/dmr/DMRGateway.ini`, host em `/var/lib/2pny/mmdvm/MMDVM-Host.ini`, perfil em `/var/lib/2pny/network-radio.json`, estado ao vivo em `/run/2pny/live-state.json`. Há `[XLX Network]` separada de `[DMR Network 1]` para BM; não imponha roteiros genéricos `/etc/dmrgateway`, `[DMR Network 2]` ou `/run/pu2pny/live_status.json` sem verificar. Nextion pela porta do modem não deve abrir diretamente `/dev/serial0` em outro processo; COMOK ou teste real é necessário para confirmar display físico. Endereço I²C não comprova modelo nem tamanho. A tela PD0DIB/ON7LDS possui HMI próprio de boot; o renderer Linux redesenha apenas após iniciar, sem copiar/gravar o HMI ou garantir identidade pixel a pixel com mockups antigos.

Usar SentinelX/VPS quando aplicável, mas VPS não prova RF, UART, Nextion ou Raspberry. Sem dados falsos de BER, RSSI, Internet, chamadas ou relógio. Ausência de fonte = `—`/indisponível. Sem senhas, tokens ou credenciais em código, logs e respostas. Evitar polling e escrita excessiva no SD. Operação normal sem terminal.

Níveis: DOC (análise), SW (teste/CI), VPS (Linux remoto), HW (Raspberry + RF/display real), PROD (uso aprovado). Teste CI não vira HW. Para cada entrega registrar versão, commit, run, hash, link do artefato e pendências de teste.
